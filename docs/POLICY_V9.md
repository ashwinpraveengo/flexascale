# FlexaScale v9: the second laptop (Windows 11, RTX 3050), a fresh fair-HPA evaluation

Sections 1–6 were written on 2026-10-28 between 22:40 and 23:40 IST, **before any v9 calibration, training or evaluation run**. They are not edited after results are seen; corrections are added as dated notes in §8. The running record (§8) is in time order.

## 1. Why a new round

v7 is on par with a fairly tuned HPA on the first laptop (Fedora, `docs/V7_REPORT.md`). The project now runs on a second laptop, and the testbed is measurably different. Nothing calibrated or fitted on the first laptop transfers:

| | First laptop (v7) | This laptop (v9) |
| :--- | :--- | :--- |
| Host | Fedora 43, Docker, Minikube 9 GiB | Windows 11, Docker Desktop (WSL2 VM, 7.9 GB), Minikube profile 6 GB / **4 vCPU**, AMD Ryzen 7 6800H, RTX 3050 4 GB |
| Load at 25 users | Light: HPA-tuned kept all 16 services at 1 replica | **CPU-pressured**: in a FlexaScale flash_sale demo run (2026-10-28 22:39, `reports/experiments_demo/`) order-service ran at 180% of its CPU request and native HPA's rule asked for 9 replicas |
| Telemetry | cAdvisor with container labels | cAdvisor reports **pod-level cgroups only** (Docker runtime, cgroup v2); fixed in `metrics/workload_metrics.py` |
| HPA's CPU signal | metrics-server | metrics-server, `--metric-resolution=60s` (checked); Prometheus scrapes cAdvisor every 10 s |

### 1.1 Defects found and fixed before any v9 run (none touches a controller's decisions)

* The lab could not start a process on Windows (`os.getpgid`, `/proc`); SB3 checkpoints could not be loaded on Windows (PyTorch zip-stream bug, `rl/sb3_compat.py`); start/stop scripts sourced an untracked file; `localhost` cost 2 s per Prometheus query (IPv6 first, port-forward bound to IPv4 only).
* **Telemetry:** CPU and memory were missing for every service on this cluster (no `container` label), so FlexaScale would have held every service ("telemetry_unavailable"). Request rates were **double-counted** where a pod is scraped by a ServiceMonitor *and* the annotation job. A scraped service with no requests was reported as "missing" rather than 0 req/s. The host-load check had the same cAdvisor gap.
* Tests: `tests/test_workload_metrics.py` (new), process and script tests made portable; full suite green on Windows (§8).

### 1.2 Hypothesis

In a CPU-pressured regime, scaling decisions change latency, so there is room for a better controller than in v7's light-load regime. A per-service graph policy that reacts on 10 s telemetry and sees where load comes from (callers) could reduce SLO violations and p95 against a CPU-target HPA that sees a 60 s metric window, at similar cost. This is tested, not assumed.

## 2. GPU assessment (measured, `scripts/profile_training.py`, `reports/v9/training_profile.jsonl`)

v7's training set-up (focal graph policy, 42,566 parameters, `FOCAL_PPO_KW`), timed per phase on CPU:

| CPU threads | rollout s | PPO update s | update share | agent-steps/s |
| ---: | ---: | ---: | ---: | ---: |
| 2 (train_v7 default) | 3.71 | 19.19 | 84% | 1,341 |
| 4 | 3.73 | 18.68 | 83% | 1,371 |
| 8 | 4.46 | 14.85 | 77% | 1,591 |

The PPO update (batched message passing, 10 epochs × 10 mini-batches of 512 per iteration) dominates; more CPU threads barely help (small tensors, overhead-bound). A GPU can only shorten the update, so the bound on the whole-training speed-up is about 6×. Decision rule (fixed now): train on the GPU if the same script on `cuda` gives ≥ 1.5× the agent-steps/s of the best CPU setting; otherwise on CPU. The device changes speed, never the protocol, seeds or selection. The live operator keeps CPU inference (one forward pass per decision); the GPU build lives in a separate training venv (`.venv-gpu`), never in the lab or the operator image.

## 3. Fair baselines on this laptop

* **HPA-default** (`hpa`): the deployed HPAs, 70% CPU target of request, 1–10 replicas, Kubernetes default behaviour (300 s scale-down stabilisation).
* **HPA-tuned** (`hpa_tuned`): the calibration rule of `docs/POLICY_V7.md` §2.1, **unchanged**, re-run here: grid {70, 150, 250, 350}% of request, 60 s scale-down window for every value, workload `calibration_steady` (25 users, 300 s), 2 runs per value in the order of `random.Random(9)` (`scripts/v9_plan.py calibration` → `reports/v9/calibration_plan.json`, labels `v9cal-<target>`). Rule: the highest T for which T and every lower value meet, on the mean of their valid runs, p95 ≤ 1.10 × p95(70), mean latency ≤ 1.10 × mean(70), failures ≤ failures(70) + 0.10 pp. `scripts/analyze_v7_calibration.py --prefix v9cal- --out reports/v9/calibration`. Invalid runs (§4) are rerun once.
* Not tested (limitation, stated in advance): per-service hand-tuned HPA targets, custom-metric HPAs (prometheus-adapter) and a faster metrics-server resolution. Each could close a gap FlexaScale shows; the HPA arms use the cluster's metrics-server as installed.

## 4. Validity of a live run (fixed now; uses no outcome metric)

A run counts only if: state completed with ≥ 95% of its duration; settled comparable start (data reset, every service at its minimum); cleanup verified safe; **on AC power in every sample** (the lab now records `host.on_ac` every 5 s); and **not host-affected**: the mean whole-machine CPU (psutil, includes the WSL2 VM) minus the Kubernetes containers' CPU (Prometheus, pod-level fallback) over the load window must not exceed the idle baseline + 2.0 cores. The idle baseline is measured once before the first calibration run, with the lab, port-forwards and tunnel running and no load (`reports/v9/host_baseline.json`). `scripts/check_host_load.py` applies this to every run. Power plan during all runs: the vendor "Turbo" plan (checked 22:55, no balanced overlay on AC); the laptop is kept awake for the batch. An invalid run is rerun once at the end of its batch.

## 5. Candidates and training

* **FlexaScale-RL** (`flexascale`, variant `v9` if it passes the gate below, else `v7`): the graph policy under the operator's safety layer, no Auto rules.
* **FlexaScale-Auto** (`auto`, same variant): Auto's per-service rules choose between the policy and HPA (HPA settings: HPA-tuned's).
* **v9 training** (only after the calibration batch; never while a live run is on): refit the application twin to **this laptop's** runs only (`scripts/fit_twin.py`, restricted to runs labelled `v9cal-*` and later), check it against those runs' replica-hours and p95 (reported, no threshold tuning after training starts), then the v7 protocol unchanged: warm start from the validation-best rule of the `limit_target` family, PPO fine-tuning (`FOCAL_PPO_KW`), seeds {1, 2}, graph and no-graph (ablation) variants, selection by mean validation reward over the 40 validation workloads; the selected run's warm start counts as a candidate too.
* **Gate (fixed now):** v9 becomes the RL arm only if its validation reward beats v7's on the refitted twin. Test-set results (twin T1, 6 live scenarios × 5 seeds) are reported with the graph ablation and the HPA-tuned twin controller, whatever they show.
* The deployed default policy of `config/apps/shopping.yaml` is switched to the RL arm's model before the evaluation (the dashboard and the demo then show the evaluated policy).

## 6. Pre-registered live evaluation

* 12 blocks: 6 scenarios (steady_browsing, checkout_heavy, payment_degradation, flash_sale, gradual_ramp, traffic_drop) × 2 repeats; arms **HPA-default, HPA-tuned, FlexaScale-RL, FlexaScale-Auto** back to back in each block, in the order of `random.Random(2910 + block)`; labels `v9-bNN-<arm>`; 25 users, spawn 5/s, 300 s, comparable start (`scripts/v9_plan.py evaluation --arms reports/v9/arms.json`, executed by `scripts/run_plan.py`). HPA arms run FlexaScale in shadow mode so every arm runs the same host processes.
* Pairing within block, Δ = candidate − reference. **Primary reference: HPA-tuned**; secondary: HPA-default. Statistics and verdict table: `docs/POLICY_V7.md` §3.3–§3.5 unchanged (95% t-intervals over blocks; "beats on cost", "beats on performance", "on par", "worse"), plus the §3.7 environment-parity rule (in steady_browsing a candidate's shop must not run > 10% faster per request than HPA-tuned's). A verdict needs ≥ 6 complete blocks; otherwise the result is reported as preliminary.
* Stopping rule: blocks run in order. If the batch has to stop (time, power), only whole blocks count, and the stop is decided by the clock, never by a result.
* Descriptive (no verdict): p50/p90/p99, SLO-violation seconds, CPU and memory, average/peak replicas, scaling events and oscillations, recovery time after load drops, estimated cost (AWS Fargate list prices on requested CPU/memory, `config/apps/shopping.yaml`).

## 7. What would and would not count

"Beats tuned HPA" is claimed only from the §6 verdict against HPA-tuned. A win against HPA-default alone is reported as such and is not presented as beating a tuned HPA. Twin results are never presented as live results.
